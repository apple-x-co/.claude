## Context

- Current branch: !`git branch --show-current`
- Remote branches: !`git branch -r`

**重要**: Context の情報は参考程度です。PR 内容の生成には、ステップ4で明示的に取得するベースブランチとの差分コミットのみを使用してください。

## Your task

現在のブランチから GitHub の Pull Request を作成します。ブランチ一覧から選択可能なマージ先を提示し、コミット内容を分析して適切な PR タイトルと本文を生成します。

### ステップ1: 事前チェック

1. **gh CLI の認証確認**:
    - `gh auth status` の結果を確認
    - 未認証の場合は「`gh auth login` で認証してください」と通知して終了

2. **現在のブランチ確認**:
    - `git branch --show-current` で現在のブランチを取得
    - `main` または `master` または `develop` の場合は「デフォルトブランチからは PR を作成できません。feature ブランチに切り替えてください」と通知して終了

3. **リモートとの同期確認**:
    - `git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null` でリモート追跡ブランチの存在を確認
    - 存在しない場合は「リモートブランチが設定されていません。`git push -u origin <branch-name>` で push してください」と通知して終了

### ステップ2: マージ先ブランチの選択

1. **利用可能なブランチ一覧を取得**:

   まず、リモートブランチの生データを取得:
   ```bash
   git branch -r
   ```

   次に、Claude がこのデータを処理して以下を行う:
    - `origin/` プレフィックスを削除
    - `HEAD` を除外
    - 現在のブランチを除外
    - 重複を削除
    - ソート

   または、以下のコマンドを使用（allowed-tools で許可されている場合）:
   ```bash
   git branch -r | grep -v HEAD | sed 's|origin/||' | grep -v "^$(git branch --show-current)$" | sort -u
   ```

2. **候補ブランチの優先順位付け**:
    - `develop`, `main`, `master` を優先的に表示
    - その他のブランチもアルファベット順で表示
    - 現在のブランチは除外

3. **`AskUserQuestion` でマージ先を選択**:
    - `question`: "PR のマージ先ブランチを選択してください"
    - `header`: "Base branch"
    - `multiSelect`: `false`
    - `options`: ブランチ一覧を配列で指定
        - `develop` が存在する場合は最初に配置（推奨）
        - 各 `label` にはブランチ名
        - 各 `description` には「推奨」「本番」「メインブランチ」などの説明を付与
    - デフォルト選択: `develop` が存在する場合は `develop`、なければ `main` または `master`

### ステップ3: 既存 PR のチェック

1. **同じブランチからの PR が既に存在するか確認**:
   ```bash
   gh pr list --head $(git branch --show-current) --base <選択されたベースブランチ> --json number,title,state,url
   ```

   出力例:
   ```json
   [
     {
       "number": 123,
       "title": "ユーザー認証機能を追加",
       "state": "OPEN",
       "url": "https://github.com/owner/repo/pull/123"
     }
   ]
   ```

   空配列 `[]` の場合は既存 PR なし。

2. **既存 PR が見つかった場合の処理**:

   **`AskUserQuestion` で対応方法を選択**:
    - `question`: "このブランチから <ベースブランチ> への PR が既に存在します (#番号)。どうしますか？"
    - `header`: "Existing PR"
    - `multiSelect`: `false`
    - `options`:
      ```json
      [
        {
          "label": "既存の PR を更新する（推奨）",
          "description": "新しいコミットを既存の PR に追加します。タイトルと本文は更新されません。"
        },
        {
          "label": "既存の PR のタイトル・本文を編集する",
          "description": "既存の PR のメタデータを更新します。"
        },
        {
          "label": "既存の PR をブラウザで確認する",
          "description": "既存の PR を開いて内容を確認します。"
        },
        {
          "label": "キャンセル",
          "description": "何もせずに終了します。"
        }
      ]
      ```

3. **選択に応じた処理**:

   **a) 既存の PR を更新する（推奨）**:
   ```bash
   # 最新のコミットをリモートに push
   git push origin $(git branch --show-current)
   
   # PR の URL を表示
   gh pr view <PR番号> --json url -q .url
   ```
    - 「既存の PR に最新のコミットが反映されました」と報告
    - PR の URL を表示

   **b) タイトル・本文を編集する**:
    - ステップ4（コミット差分の分析）に進む
    - ステップ5（PR 候補生成）で候補を作成
    - 選択された内容で既存 PR を更新:
      ```bash
      gh pr edit <PR番号> --title "<新しいタイトル>" --body "<新しい本文>"
      ```

   **c) ブラウザで確認**:
   ```bash
   gh pr view <PR番号> --web
   ```
    - 処理を終了

   **d) キャンセル**:
    - 「処理をキャンセルしました」と報告して終了

4. **既存 PR が見つからなかった場合**:
    - ステップ4（コミット差分の分析）に進む

### ステップ4: コミット差分の分析

**🚨 最重要制約 🚨**:
このステップでは、**以下のコマンドを実行して、その出力のみ**を使って PR 内容を生成します。
**それ以外の情報源は一切使用禁止**です。

---

**実行手順**:

**手順1**: ベースブランチとの差分コミットを取得
```bash
git fetch origin develop
git log origin/<base-branch>..HEAD --pretty=format:"%h %s%n%b" --reverse
```

**このコマンドの出力を読む**。出力に含まれるコミットのみが、この PR に含まれます。

**例1: 差分が2コミットの場合**
```
abc1234 feat: 機能Aを実装

機能Aの詳細な説明

def5678 fix: バグ修正

バグ修正の詳細
```
→ **この2つのコミットのみ**が PR の対象。過去の大規模変更（機能B実装など）は**含まれていない**ので PR に書かない。

**例2: 差分が1コミットの場合**
```
abc1234 refactor: コードリファクタリング

不要なコードを削除
```
→ **この1つのコミットのみ**が PR の対象。

**例3: 差分が0コミットの場合**
```
（出力なし）
```
→ PR を作成できない。「ベースブランチとの差分がありません」と通知して終了。

---

**手順2**: 変更ファイル一覧を取得
```bash
git diff origin/<base-branch>..HEAD --name-status
```

**このコマンドの出力を読む**。プロジェクトルートからの相対パスで表示されます。

**例**:
```
M       src/Module/FeatureA.php
A       src/Module/NewFeature.php
A       templates/feature/new.html
```
→ この3ファイルのみが変更されている。

---

**手順3**: コミット数を確認
```bash
git rev-list --count origin/<base-branch>..HEAD
```

**例**: 出力が `2` なら、2コミットが含まれる。

---

**手順4**: 変更ファイル数を確認
```bash
git diff origin/<base-branch>..HEAD --name-only | wc -l
```

**例**: 出力が `3` なら、3ファイルが変更されている。

---

**手順5**: PR 内容の生成ルール

**使用してよい情報（手順1-4で取得したもののみ）**:
- ✅ 手順1で取得したコミットメッセージとコミット本文
- ✅ 手順2で取得した変更ファイルのパス
- ✅ 手順3で取得したコミット数
- ✅ 手順4で取得した変更ファイル数

**使用禁止の情報**:
- ❌ Context セクション
- ❌ `git log --oneline -10` などの直近のコミット
- ❌ `git status` や作業ディレクトリの状態
- ❌ Claude の記憶、推測、想像
- ❌ 手順1-4の出力に含まれていない情報

**確認方法**:
PR 本文に記載する全ての情報（コミット内容、ファイル名、機能名、変更内容）が、
**手順1または手順2の出力から直接確認できる**ことを確認してください。

**具体例**:
- もし手順1の出力に「formrun 移行」というコミットがない → PR に「formrun 移行」を書かない
- もし手順2の出力に `ContactRepository.php` がない → PR に `ContactRepository.php` を書かない
- もし手順1の出力が「エラー画面を実装」の2コミットのみ → PR には**エラー画面の実装のみ**を書く

---

**🚨 重要 🚨**:
このステップを正しく実行しないと、**PR に含まれない過去の作業内容**が混入します。
手順1の出力を**必ず最初に確認**し、その出力に含まれるコミットのみから PR 内容を生成してください。

### ステップ5: PR タイトルと本文の候補生成

**必ず3つの候補を生成**し、以下の構造で作成:

#### 候補1: 詳細版（推奨）

**タイトル**:
- 形式: `<主要な変更の詳細な説明>`
- 例: `新機能Aを実装しユーザー体験を向上`
- 長さ: 50-72文字程度

**本文**:
```markdown
## 📝 概要
<変更の目的と背景を2-3文で説明>

## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>
- <主要な変更点3>

## 📊 影響範囲
- 変更ファイル数: X件
- コミット数: Y件

## 🔗 関連情報
<関連する issue や参考資料があれば記載>

## ✅ テスト
<実施したテストや確認事項>
```

#### 候補2: 標準版

**タイトル**:
- 形式: `<変更の要約>`
- 例: `新機能Aを実装`
- 長さ: 30-50文字程度

**本文**:
```markdown
## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>

📊 変更ファイル数: X件、コミット数: Y件
```

#### 候補3: 簡潔版

**タイトル**:
- 形式: `<変更内容>`
- 例: `機能A追加`
- 長さ: 20-40文字程度

**本文**:
```markdown
📝 <変更の概要を1-2文で説明>
```

**フォーマット規則**（全候補に適用）:
- **内容の情報源**: ステップ4で取得したコミット差分のみを使用
    - `git log origin/<base-branch>..HEAD` の出力のみ
    - `git diff origin/<base-branch>..HEAD --name-status` の出力のみ
    - Context や直近のコミットは参照しない
- タイトルとボディのメッセージは日本語
- タイトルは72文字以内を推奨
- 本文は Markdown 形式
- **ファイル名を記載する場合**:
    - **`git diff` の出力をそのまま使用**（プロジェクトルートからの相対パス）
    - **行番号（`:1` など）は絶対に付けない**
    - バッククォーテーション `` ` `` で囲む
- 英語と日本語の間に半角スペースを入れる

### ステップ6: PR 内容の選択

`AskUserQuestion` ツールで以下のように提示:

- `question`: "PR のタイトルと本文を選択してください"
- `header`: "Pull Request"
- `multiSelect`: `false`
- `options`: 3つの候補を配列で指定
    - 各 `label` には生成した PR タイトルを設定
    - 各 `description` には候補の特徴（「詳細版（推奨）」「標準版」「簡潔版」）と本文のプレビュー（最初の1-2行）を表示

### ステップ7: PR の作成または更新

1. **新規 PR の作成**（ステップ3で既存 PR がなかった場合）:

   **デフォルトで Draft PR として作成**:
   ```bash
   gh pr create --base <選択されたベースブランチ> \
                --title "<選択されたタイトル>" \
                --body "<選択された本文>" \
                --draft
   ```

   Draft PR として作成することで、レビュー前に内容を確認・調整できます。
   Ready にする場合は、ステップ8で `gh pr ready` を実行してください。

2. **既存 PR のメタデータ更新**（ステップ3で「タイトル・本文を編集する」を選択した場合）:
   ```bash
   gh pr edit <PR番号> \
              --title "<選択されたタイトル>" \
              --body "<選択された本文>"
   ```

3. **オプション追加（必要に応じて）**:
    - レビュワーを指定する場合: `--reviewer <username>` を追加
    - ラベルを追加する場合: `--label <label-name>` を追加
    - マイルストーンを設定する場合: `--milestone <milestone-name>` を追加

4. **エラーハンドリング**:
    - PR 作成/更新に失敗した場合:
        - エラー内容をユーザーに報告
        - 一般的なエラー原因を提示:
            - 既に同じブランチで PR が存在する（ステップ3でチェック済みだが念のため）
            - リモートブランチが最新でない
            - 権限不足
            - ネットワークエラー
    - エラー解決のための提案を提示

5. **成功時の確認**:
    - 新規作成の場合:
      ```bash
      gh pr view --json url -q .url
      ```
        - 「Draft PR が正常に作成されました」と日本語で報告
        - 「Ready にする場合は `gh pr ready` を実行してください」と案内

    - 更新の場合:
      ```bash
      gh pr view <PR番号> --json url -q .url
      ```
        - 「PR #<番号> のタイトルと本文を更新しました」と日本語で報告

    - PR の URL を表示
    - ブラウザで PR を開くかどうかを確認（オプション）

### ステップ8: 追加オプションの確認（オプション）

PR 作成後、以下の追加操作をユーザーに提案:

1. **Draft から Ready への変更**:
   ```bash
   gh pr ready <PR番号>
   ```

2. **レビュワーの追加**:
   ```bash
   gh pr edit <PR番号> --add-reviewer <username>
   ```

3. **ラベルの追加**:
   ```bash
   gh pr edit <PR番号> --add-label <label-name>
   ```

## 重要な制約

- **全てのレスポンスを日本語で行う**（分析結果、候補の説明、エラーメッセージ、成功報告など）
- **必ず3つの PR 候補を生成**（それ以上でもそれ以下でもない）
- **詳細版を1番目（推奨）に配置**する
- **デフォルトで Draft PR を作成**（`--draft` フラグを使用）
- **既存の PR との重複をチェック**（ステップ3で実施）:
    - ブランチ選択後すぐにチェックを実行
    - 既に PR が存在する場合は以下の選択肢を提示:
        1. 既存の PR を更新（コミットを追加）
        2. 既存の PR のタイトル・本文を編集
        3. 既存の PR をブラウザで確認
        4. キャンセル

### 🚨 PR 内容生成の厳格なルール 🚨

**情報源の制限（違反すると間違った PR になります）**:

✅ **使用してよい情報源（ステップ4で取得）**:
- `git log origin/<base-branch>..HEAD --pretty=format:"%h %s%n%b" --reverse` の出力
- `git diff origin/<base-branch>..HEAD --name-status` の出力
- `git diff origin/<base-branch>..HEAD --shortstat` の出力
- `git rev-list --count origin/<base-branch>..HEAD` の出力

❌ **使用禁止の情報源**:
- Context セクションの情報
- `git log --oneline -10` などの直近のコミット
- `git status` や `git diff HEAD` などの作業ディレクトリの状態
- あなたの記憶や推測
- その他、ステップ4で明示的に取得していない情報

**確認方法**:
生成した PR 内容に記載された全ての情報（コミット内容、ファイル名、変更内容など）が、ステップ4で取得したコマンドの出力から確認できることを確認してください。確認できない情報は含めてはいけません。

**具体例（これが最も重要です）**:

**ケース1: 差分が2コミット（小規模な変更）の場合**
```bash
$ git log origin/develop..HEAD --oneline
abc1234 feat: 新機能Aを実装
def5678 fix: バグ修正B
```
→ ✅ PR には「新機能Aの実装」と「バグ修正B」のみを記載
→ ❌ 「過去の大規模変更X」「機能Y」などは記載しない（差分に含まれていないため）
→ ✅ コミット数: 2件、変更ファイル数: 実際の `git diff` の結果

**ケース2: 差分が多数のコミット（大規模な機能追加）の場合**
```bash
$ git log origin/develop..HEAD --oneline
（多数のコミット分の出力、複数の機能を含む）
```
→ ✅ これらの全コミットの内容を分析して PR を生成
→ ✅ コミット数: 実際のコミット数、変更ファイル数: 実際のファイル数

**❌ 間違った例（よくある間違い）**:
```
実際の差分コミット: 2件（小規模な変更のみ）
↓
でも生成された PR には:
- 過去の大規模変更X（❌ 差分に含まれていない）
- 機能Y（❌ 差分に含まれていない）  
- 100+ファイル変更（❌ 実際は3ファイルのみ）
- 30+コミット（❌ 実際は2コミットのみ）
```
→ これは**完全に間違い**です。差分に含まれない過去の作業内容を書いています。

**✅ 正しい例**:
```
実際の差分コミット: 2件（小規模な変更のみ）
↓
生成された PR には:
- 新機能Aの実装（✅ 差分に含まれる）
- バグ修正B（✅ 差分に含まれる）
- 3ファイル変更（✅ `git diff` の実際の結果）
- 2コミット（✅ `git log` の実際の結果）
```
→ これが**正しい**です。ステップ4で取得した差分コミットの内容のみを記載しています。

### ファイル名の記載ルール

**ファイル名を記載する場合**:
- `git diff origin/<base-branch>..HEAD --name-status` の出力をそのまま使用
- プロジェクトルートからの相対パスで記載
- 行番号（`:1` など）は**絶対に付けない**
- バッククォーテーション `` ` `` で囲む

**例**:
- ✅ 正しい: `src/Module/FeatureA.php`
- ❌ 間違い: `Module/FeatureA.php`（パスが不完全）
- ❌ 間違い: `FeatureA.php`（パスが不完全）
- ❌ 間違い: `src/Module/FeatureA.php:1`（行番号が付いている）
- ❌ 間違い: \`src/Module/FeatureA.php\`（バッククォーテーションの前にバックスラッシュが付いている）

### その他の制約

- **リモートブランチが最新かチェック**:
  ```bash
  git fetch origin
  git status -sb | grep "ahead\|behind"
  ```
    - ローカルがリモートより古い場合は `git pull` を推奨
    - ローカルがリモートより新しい場合は `git push` を推奨
- **コミットが存在しない場合**:
    - 「ベースブランチとの差分がありません。変更をコミットしてから PR を作成してください」と通知して終了
- **gh CLI が利用できない場合**:
    - 「gh CLI がインストールされていません。https://cli.github.com/ からインストールしてください」と通知して終了

## 実行例

### 正常系（新規PR作成）

```
$ /ghpr

[ステップ1: 事前チェック]
✓ gh CLI 認証済み
✓ 現在のブランチ: feature/new-feature
✓ リモートブランチ設定済み

[ステップ2: マージ先ブランチ選択]
> develop (推奨)
  main (メインブランチ)
  staging (ステージング環境)

[ステップ3: 既存PRチェック]
✓ 既存のPRは見つかりませんでした

[ステップ4: コミット差分分析]
手順1: ベースブランチとの差分コミットを取得
$ git log origin/develop..HEAD --pretty=format:"%h %s%n%b" --reverse

出力:
abc1234 feat: 新機能Aを実装

新機能Aの詳細な説明

def5678 fix: バグ修正B

バグBの修正内容

→ ✅ この2つのコミットのみが PR の対象
```

## Tips

- **複数の変更種別が混在する場合**:
    - 最も重要な変更の種別を type として使用
    - 本文で各種別の変更を分けて説明

- **Breaking Changes がある場合**:
    - タイトルに⚡️を追加: `⚡️API 仕様を変更`
    - 本文に `## ⚠️ Breaking Changes` セクションを追加

- **Issue 番号を含める場合**:
    - 本文の最後に `Closes #123` または `Fixes #456` を追加
    - GitHub が自動的に Issue とリンク

- **Draft PR から Ready にする場合**:
    - PR 作成後に `gh pr ready` コマンドを実行
    - または、GitHub の Web UI から "Ready for review" ボタンをクリック
