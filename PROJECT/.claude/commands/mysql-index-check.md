## Your task

MySQLのスキーマ定義ファイルとSQLクエリファイルのアクセスパターンを照合し、**本当に不足しているインデックスだけ**を正確に特定します。

---

### ステップ1: 前提情報の確認

`AskUserQuestion` を使い、以下の3つをユーザーに確認する：

1. **スキーマ定義ファイルの格納ディレクトリ**（`CREATE TABLE` 文が含まれる `.sql` ファイル群）
2. **SQLクエリファイルの格納ディレクトリ**（`SELECT` などのクエリが含まれる `.sql` ファイル群）
3. **MySQL のバージョン**（例: `5.7`、`8.0`、`8.4` など）

> **バージョン別の考慮点**:
> - **8.0 以降**: 降順インデックス (`DESC`)・関数インデックス・不可視インデックス (`INVISIBLE`) が利用可能。`ORDER BY col DESC` のようなパターンでは降順インデックスが有効。
> - **5.7 以前**: 降順インデックス不可。`ORDER BY col DESC` での最適化は制限される。その旨を結果に注記すること。

確認後、各ディレクトリ配下のファイル一覧を取得してから分析を開始する。

---

### ステップ2: スキーマの解析（インデックス済みカラムの抽出）

各スキーマファイルを読み、テーブルごとに「インデックス済み」とみなすカラムを以下の**3種類すべて**から抽出する：

| 種別 | 定義パターン | 扱い |
|------|------------|------|
| PRIMARY KEY | `PRIMARY KEY (col)` | そのカラム |
| 明示的インデックス | `CREATE INDEX idx ON tbl (col1, col2)` | 左端から有効なプレフィックス |
| FK自動インデックス | `CONSTRAINT fk FOREIGN KEY (col) REFERENCES ...` | そのカラム（InnoDB が自動作成） |

> **重要**: FK制約が定義されているカラムには InnoDB が自動でインデックスを作成する。明示的な `CREATE INDEX` がなくても「インデックスあり」として扱うこと。

複合インデックス `(col1, col2, col3)` の場合：
- `col1` 単独での検索 → 有効
- `col1, col2` での検索 → 有効
- `col2` 単独での検索 → **無効**（左端プレフィックスのみ）

---

### ステップ3: クエリのアクセスパターン解析

各SQLクエリファイルを読み、テーブル名を特定した上で以下を抽出する：

**インデックスが効果的なパターン（抽出対象）：**
- `WHERE` 句で使われているカラム
- `JOIN ... ON` 句で使われているカラム
- `WHERE` 句を伴わない `ORDER BY` 句のカラム（フルスキャン＋ソートが発生するため）

**インデックスが不要なパターン（除外）：**
- `GROUP BY` のみに使われているカラム（`WHERE` で絞り込んだ後の `GROUP BY` にはインデックスは使われない）
- `SELECT` 句のみに登場するカラム
- `INSERT` / `UPDATE` のみに使われているカラム
- レコード数が極めて少ないマスターテーブル（種別コード等、数十件以下）はフルスキャンの方が高速なためインデックス不要

---

### ステップ4: 突き合わせ

ステップ2のインデックス済みカラムと、ステップ3のアクセスパターンを照合する。

インデックスが存在しないにもかかわらず、WHERE / JOIN ON / ORDER BY で使われているカラムを「不足候補」として特定する。

**補足判断：**
- `IS NULL` / `IS NOT NULL` の条件はカーディナリティが低い（ほぼ全件が NULL または非 NULL）場合、インデックスがあってもオプティマイザが使わないことが多い。その旨を注記すること。
- 既存の複合インデックスで左端プレフィックスとしてカバーされている場合は「不足なし」とすること。

---

### ステップ5: 結果の報告

不足が見つかったテーブルのみ報告する。不足のないテーブルはスキップしてよい。

各テーブルの報告形式：

```
### テーブル名（コメント名があれば併記）
**既存インデックス**:
- PRIMARY: col
- idx_xxx: (col1, col2) → col1 単独・(col1, col2) プレフィックスが有効
- FK自動: col → 参照先テーブル.col

**不足インデックス候補**:
| カラム | 使用パターン | クエリ数 | 代表クエリファイル名 |
|-------|------------|---------|-----------------|
| col   | WHERE      | N       | xxx.sql         |

**推奨 SQL**:
\`\`\`sql
CREATE INDEX idx_テーブル名_N ON テーブル名 (col);
\`\`\`
```

最後に以下の総括サマリーを出力する：

```
## 総括

- 分析テーブル数: N
- 分析クエリ数: N
- 不足インデックスが見つかったテーブル: N
- 検出された不足インデックス総数: N

### 優先度別まとめ
- 高（WHERE/JOIN ON で頻繁に使用）: ...
- 中（WHERE で使用、クエリ数少）: ...
- 低（IS NULL パターン等、効果が限定的）: ...
```

---

## 重要な制約

- **FK自動インデックスを「不足」として報告しないこと**（最も多い誤報告パターン）
- **GROUP BY のみのカラムをインデックス候補にしないこと**
- 全レスポンスを日本語で行うこと
