# 修正・変更依頼

既存のコードベースに対する修正・変更依頼を、安全かつ正確に実装する。

単に依頼されたコードを書くのではなく、**既存のコード・設計・仕様を調査し、必要な場合は利用者に確認し、検証まで行うこと**を目的とする。

---

## 基本原則

以下の原則を常に守る。

1. **曖昧な仕様を推測して実装しない。**
2. **既存のコード・設計・規約を理解してから変更する。**
3. **既存の設計を尊重し、不要な新規設計を持ち込まない。**
4. **依頼を満たすために必要な最小限の変更を優先する。**
5. **依頼と無関係なリファクタリングを行わない。**
6. **重要な設計・仕様判断を勝手に決定しない。**
7. **実装後は可能な限りテスト・静的解析・差分確認を行う。**
8. **確認できていないことを、確認済みであるかのように報告しない。**

---

# Phase 1: 依頼内容を理解する

まず、利用者の依頼を理解する。

この段階では、まだファイルを変更しない。

以下を整理する。

- 何を変更する必要があるか
- どのような状態になれば依頼を満たすのか
- 現在の挙動と期待する挙動は何か
- 変更してはいけない既存の挙動は何か
- 利用者から明示された制約は何か
- 依頼文から読み取れる前提条件は何か

依頼内容だけでは判断できない重要な事項がある場合は、後述の「不明点の扱い」に従う。

---

# Phase 2: コードベースを調査する

実装を開始する前に、関連する既存コードを調査する。

必要に応じて以下を確認する。

- 対象となるクラス・関数・ファイル
- 対象コードの呼び出し元
- 関連するドメインオブジェクト
- UseCase / Service / Repository などの関連コンポーネント
- 関連するテスト
- 関連する設定
- 類似する既存実装
- データベースやAPIへの影響
- Gitの履歴が有用な場合は `git log` や `git blame`

利用者が指定したファイルだけを調査対象と決めつけない。

変更によって影響を受ける可能性のあるコードも確認する。

---

# Phase 3: 不明点・リスクを確認する

調査結果を踏まえ、実装に必要な情報が十分に揃っているか判断する。

## 利用者に確認するべきケース

以下のような場合は、推測して実装せず、利用者に確認する。

- 仕様を複数の方法に解釈できる
- ビジネスルールが明確でない
- 既存仕様と今回の依頼が矛盾している
- 複数の設計方針があり、結果に意味のある違いがある
- DB設計に複数の妥当な選択肢がある
- APIの仕様変更について判断できない
- 後方互換性を維持すべきか判断できない
- エラー時の挙動が決まっていない
- データ移行の要否や方法が不明
- 既存の重要な仕様を変更する可能性がある
- 変更範囲が当初の依頼から大きく広がる
- 実装する前に利用者の承認が必要だと判断できる

### 重要

**実装結果に影響する重要な不明点を、都合よく推測して解決してはいけない。**

必要な場合は、調査した内容と選択肢を簡潔に説明したうえで質問する。

質問した場合は、回答を得るまで該当する実装を進めない。

---

# Phase 4: 実装方針を決める

仕様が十分に明確になったら、実装方針を決める。

必要に応じて、実装前に以下を簡潔に提示する。

## 理解

依頼内容をどのように理解したか。

## 調査結果

既存コードについて分かったこと。

## 実装方針

- どのファイル・コンポーネントを変更するか
- それぞれ何を変更するか
- どのテストを追加・変更するか
- DBやAPIなどへの影響
- その他、注意すべき点

ただし、単純かつ局所的な変更については、過剰に詳細な計画を作成する必要はない。

**変更の複雑さに応じて計画の粒度を調整する。**

---

# Phase 5: 実装する

決定した方針に従って実装する。

以下を優先する。

- 既存の設計
- 既存の抽象化
- 既存の命名規則
- 既存のコーディング規約
- 既存のエラーハンドリング
- 既存のテストパターン

新しい抽象化や仕組みを追加する場合は、それが本当に必要か検討する。

依頼と関係のないリファクタリングは行わない。

---

## 実装中に新しい問題が見つかった場合

実装中に、当初の調査では分からなかった重要な問題が判明した場合は注意する。

以下の場合は、無理に実装を続けない。

- 当初の方針では仕様を満たせない
- 新しい設計判断が必要になった
- 変更範囲が大幅に広がった
- 既存仕様との矛盾が判明した
- データ破壊や重大な互換性問題につながる可能性がある

この場合は利用者に状況を説明し、必要に応じて確認する。

---

# Phase 6: テスト・検証する

実装後、変更が正しく動作することを検証する。

まず変更に直接関係するテストを実行する。

プロジェクトで利用している場合は、必要に応じて以下も実行する。

- PHPUnit
- PHPStan
- PHPCS
- その他の静的解析
- その他のプロジェクト固有のチェック

可能な範囲で、

1. 変更対象のテスト
2. 関連する既存テスト
3. 静的解析
4. コーディング規約チェック

の順に確認する。

---

## テストが失敗した場合

テストが失敗した場合は、単にテストを変更して成功させようとしてはいけない。

以下を確認する。

1. 失敗原因を確認する
2. 今回の変更による失敗なのか確認する
3. 実装に問題があれば修正する
4. 既存の問題であれば、その事実を報告する
5. 期待する仕様自体が変更された場合は、テストを変更する必要性を判断する

**テストを通すこと自体を目的にしない。**

---

# Phase 7: 差分をレビューする

実装と検証が終わったら、変更内容を自分でレビューする。

可能であれば `git diff` を確認する。

以下を確認する。

- 依頼された変更が正しく実装されている
- 不要な変更が含まれていない
- 無関係なファイルを変更していない
- デバッグコードが残っていない
- 不要なコメントが追加されていない
- 不要なリファクタリングを行っていない
- 意図しないフォーマット変更がない
- 既存の設計・規約に沿っている
- テストが適切に追加・変更されている
- 依頼内容と最終的な実装に矛盾がない

問題があれば、完了報告の前に修正する。

---

# 完了報告

作業が完了したら、以下の内容を簡潔に報告する。

## 変更内容

何を変更したか。

## 検証

実際に実行したテスト・静的解析・その他のチェックと、その結果。

## 注意事項

必要に応じて以下を記載する。

- 未実行のテスト
- 残っている問題
- 仕様上の注意点
- 将来的に検討すべき事項

**実際に実行していないテストを「成功した」と報告してはいけない。**

---

# 自律性の判断

このコマンドでは、すべての判断を利用者に確認する必要はない。

以下のように判断する。

### 自律的に判断してよいもの

- 既存コードから明確に読み取れる実装方法
- 既存プロジェクトの規約に従った実装
- 明確な仕様を満たすための細かな実装上の判断
- 既存パターンに沿ったテストの追加
- 明らかな不要コードの整理

### 利用者に確認するもの

- ビジネスルール
- 仕様の解釈
- 重要な設計判断
- 互換性に関する判断
- DB設計
- API仕様
- データ移行
- 破壊的変更
- 複数の妥当な選択肢から選択する必要がある事項

---

# 最重要ルール

**「分からないことを、分かったことにして実装しない。」**

コードベースから合理的に判断できることは自律的に進める。

しかし、コードベースから判断できない仕様や重要な設計判断については、利用者に確認する。

目的は、利用者への確認を増やすことではなく、

**AIが自律的に進められる部分は最大限自律的に進め、重要な判断だけを利用者に戻すこと。**
