## Context

- Current branch: !`git branch --show-current`
- Remote branches: !`git branch -r`

**重要**: Context のブランチ情報はそのまま利用してよい（再取得しない）。ただし PR の**内容**の生成には、ステップ3で取得する差分のみを使用すること。

## Your task

GitHub のリモートブランチ同士（head → base）の Pull Request を作成します（詳細版）。3つの PR 候補と影響範囲テーブルを生成します。`Current branch` は head / base の推奨を決めるためだけに使い、PR の内容や差分は常にリモートの状態（`origin/<base>...origin/<head>`）から生成します。push 前のローカルコミットは対象外です。

### ステップ1: ブランチ候補の整理

Context の `Remote branches`（`git branch -r` の出力）を処理対象とする（再取得しない）:
- `origin/` プレフィックスを削除
- `HEAD` を含む行（`origin/HEAD -> origin/main` など）を除外
- 重複を削除・ソート

候補が2件未満の場合は「PR を作成できるリモートブランチが足りません」と通知して終了。

### ステップ2: head / base の選択

**推奨ブランチの決定**（質問の前に決める）:
- **推奨 head**: `Current branch` がステップ1の候補に含まれ、かつ `develop` / `main` / `master` 以外ならそのブランチ。それ以外は `develop`（なければ `main` / `master`）
- **推奨 base**: 推奨 head が `develop` なら `main`（なければ `master`）。それ以外は `develop`（なければ `main` / `master`）

`AskUserQuestion` で **2つの質問を1回で**提示する:

1. 質問1: "PR の head（マージ元）ブランチを選択してください"
    - `header`: "Head branch"
    - `multiSelect`: `false`
    - `options`: 推奨 head を先頭（推奨）にし、続けてその他のブランチ（最大4件）
2. 質問2: "PR の base（マージ先）ブランチを選択してください"
    - `header`: "Base branch"
    - `multiSelect`: `false`
    - `options`: 推奨 base を先頭（推奨）にし、続けてその他のブランチ（最大4件）

推奨に該当するブランチが存在しない場合は、存在するブランチのみで候補を構成する。

選択後、head と base が同一の場合は「head と base に同じブランチは指定できません」と通知して終了。

### ステップ3: 既存 PR のチェック・差分分析（統合）

**🚨 最重要制約 🚨**:
このステップでは、**以下のコマンドを実行して、その出力のみ**を使って PR 内容を生成します。**それ以外の情報源は一切使用禁止**です。

`<head>` / `<base>` にはステップ2で確定した値をリテラル文字列として代入する（shell substitution 不可）。

```bash
echo "=== EXISTING_PR ==="
gh pr list --head <head> --base <base> --state all --json number,title,state,url
echo "=== COMMITS ==="
git fetch --no-tags --quiet origin <head> <base> && git log origin/<base>..origin/<head> --pretty=tformat:"### %h %s%n%b" --reverse
echo "=== FILES ==="
git diff origin/<base>...origin/<head> --name-status
echo "=== NUMSTAT ==="
git diff origin/<base>...origin/<head> --numstat
echo "=== STAT ==="
git diff origin/<base>...origin/<head> --shortstat
```

- `git diff` は三点（`...`）で、base との共通祖先から head までの変更のみを対象にする（PR の差分と一致させる）

**`gh` が認証エラーを返した場合**: 「`gh auth login` で認証してください」と通知して終了

**読み取りルール**:
- **既存 PR** = `EXISTING_PR` 区画のうち `state` が `OPEN` または `DRAFT` のもの（`MERGED` や `CLOSED` は除外）
- **コミット数** = `COMMITS` 区画の `### ` で始まる行数
- **変更ファイル一覧と新規/更新/削除** = `FILES` 区画の `A` / `M` / `D`
- **ファイルごとの追加・削除行数** = `NUMSTAT` 区画
- **変更ファイル数 / 追加・削除行数（合計）** = `STAT` 区画の `N files changed, N insertions(+), N deletions(-)`

**差分が0コミットの場合**: 「base との差分がありません」と通知して終了

**既存 PR が見つかった場合**:

head は既にリモートにあるため、新しいコミットは既存 PR に自動で反映される。push は行わない。

`AskUserQuestion` で対応方法を選択:
- `question`: "<head> から <base> への PR が既に存在します (#番号)。どうしますか？"
- `header`: "Existing PR"
- `multiSelect`: `false`
- `options`:
    - "既存の PR のタイトル・本文を再生成する（推奨）": 最新の差分で PR 内容を更新します
    - "既存の PR を無視して新規 PR を作成する": 通常は推奨されません
    - "既存の PR をブラウザで確認する"
    - "キャンセル"

**選択に応じた処理**:
- **再生成**: ステップ4〜6に進み、生成後に `gh pr edit <PR番号> --title "..." --body "..."` で更新。`EXISTING_PR` の `url` を表示
- **新規作成**: ステップ4〜6に進み、新規 PR 作成フローを実行
- **ブラウザ**: `gh pr view <PR番号> --web` を実行して終了
- **キャンセル**: 「処理をキャンセルしました」と報告して終了

**既存 PR が見つからなかった場合**: そのままステップ4に進む

### ステップ4: 変更の分類

コミットメッセージとファイルパスから、変更を意味のあるカテゴリ（Cohort）にグループ化する。

**カテゴリ化の基本原則**:
1. **ファイルの役割や変更の目的でグループ化**: 同じ機能や目的に関連するファイルをまとめる。ディレクトリ構造とコミットメッセージから関連性を判断する
2. **カテゴリ名は変更の内容を反映**: 「何を」変更したかを明確にする。プロジェクト固有の用語を使ってよい
    - 追加系: 「〜の実装」「〜の追加」
    - 更新系: 「〜の更新」「〜の改善」
    - 削除系: 「〜の削除」「〜のクリーンアップ」
3. **1カテゴリあたり 3-5 ファイル程度**: 多すぎる場合は適切に分割する。コミット数が多いリリース PR では、カテゴリ単位で要約し、ファイルは代表的なもののみ列挙してよい

**変更概要の生成ルール**:
- コミットメッセージを主な情報源として使用する
- 技術的な詳細（追加された機能、変更された振る舞い、クラス名、関数名など）を含める
- 変更の理由や目的を明確にする
- 2-4文程度にまとめる

### ステップ5: PR タイトルと本文の候補生成

**必ず3つの候補を生成**し、以下の構造で作成:

#### 候補1: 詳細版（推奨）

**タイトル**: `<主要な変更の詳細な説明>`（50-72文字程度）

**本文**:
```markdown
## 📝 概要
<変更の目的と背景を2-3文で説明>

## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>
- <主要な変更点3>

## 🎯 影響範囲

| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| <カテゴリ名1><br>`<ファイルパス1>` | <変更内容の詳細な説明1> |
| <カテゴリ名2><br>`<ファイルパス2>`<br>`<ファイルパス3>` | <変更内容の詳細な説明2> |

**変更統計**:
- 変更ファイル数: X件
- コミット数: Y件
- 追加: +N行
- 削除: -M行

## 🔗 関連情報
<関連する issue や参考資料があれば記載>

## ✅ テスト
<実施したテストや確認事項>
```

**影響範囲テーブルのルール**:
- カテゴリ名の後に `<br>` を入れ、ファイルパスをバッククォートで囲んで続ける（複数ファイルは `<br>` で区切る）
- セル内の改行は `<br>` を使用する
- ヘッダー行の下に区切り線 `|---|---|` を入れる
- 変更概要は技術的な詳細を含めて 2-4文で記述する

**テーブル例**:
```markdown
| 認証コンポーネントの実装<br>`src/components/LoginForm.tsx`<br>`src/components/SignupForm.tsx` | ユーザー認証用のログインとサインアップフォームコンポーネントを実装。バリデーション、エラーハンドリング、ローディング状態の管理を含む。 |
| 認証フック<br>`src/hooks/useAuth.ts` | 認証状態管理のためのカスタムフックを追加。ログイン、ログアウト、トークン管理の機能を提供。 |
```

#### 候補2: 標準版

**タイトル**: `<変更の要約>`（30-50文字程度）

**本文**:
```markdown
## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>

## 🎯 影響範囲

| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| <カテゴリ名1><br>`<ファイルパス1>` | <簡潔な変更説明1> |
| <カテゴリ名2><br>`<ファイルパス2>` | <簡潔な変更説明2> |

🎯 変更ファイル数: X件、コミット数: Y件
```

#### 候補3: 簡潔版

**タイトル**: `<変更内容>`（20-40文字程度）

**本文**:
```markdown
📝 <変更の概要を1-2文で説明>

🎯 変更ファイル数: X件、コミット数: Y件
```

**フォーマット規則**（全候補に適用）:
- タイトルと本文は日本語、タイトルは72文字以内を推奨、本文は Markdown 形式
- 英語と日本語の間に半角スペースを入れる
- **ファイル名を記載する場合**:
    - `git diff --name-status` の出力をそのまま使用（プロジェクトルートからの相対パス）
    - 行番号（`:1` など）は付けない
    - バッククォートで囲み、**バックスラッシュでエスケープしない**（テーブル内も同様）
        - ✅ 正しい: `src/Module/FeatureA.php`
        - ❌ 間違い: \`src/Module/FeatureA.php\`

### ステップ6: PR 内容の選択と作成/更新

1. **`AskUserQuestion` で候補を選択**:
    - `question`: "PR のタイトルと本文を選択してください"
    - `header`: "Pull Request"
    - `multiSelect`: `false`
    - `options`: 3つの候補を配列で指定
        - 各 `label` には生成した PR タイトルを設定
        - 各 `description` には候補の特徴（「詳細版（推奨）」「標準版」「簡潔版」）と本文のプレビュー（最初の1-2行）を表示

2. **新規 PR の作成**（デフォルトで Draft PR）:
   ```bash
   gh pr create --head <head> \
                --base <base> \
                --title "<選択されたタイトル>" \
                --body "<選択された本文>" \
                --draft
   ```

3. **既存 PR の更新**（ステップ3で「再生成」を選択した場合）:
   ```bash
   gh pr edit <PR番号> \
              --title "<選択されたタイトル>" \
              --body "<選択された本文>"
   ```

4. **成功時の確認**:
    - 新規作成: `gh pr create` の出力から URL を読み取り、「Draft PR が正常に作成されました」と報告
    - 更新: `EXISTING_PR` の `url` を表示し、「PR #<番号> のタイトルと本文を更新しました」と報告
    - 「Ready にする場合は `gh pr ready <PR番号>` を実行してください」と案内

5. **エラーハンドリング**: 失敗時はエラー内容を報告し、原因候補（権限不足、head/base が存在しない、ネットワークエラー）を提示

## 重要な制約

- **全てのレスポンスを日本語で行う**
- **ローカルの状態（未 push のコミット、作業ツリー）は PR 内容に一切使用しない**
- **`git push` は実行しない**（リモートブランチ間の PR のため不要）
- **必ず3つの PR 候補を生成**し、**詳細版を1番目（推奨）に配置**する
- **詳細版には必ず影響範囲テーブルを含める**
- **デフォルトで Draft PR を作成**
- **既存の PR との重複をチェック**（ステップ3）

### 🚨 PR 内容生成の厳格なルール 🚨

✅ **使用してよい情報源**: ステップ3で取得した `COMMITS` / `FILES` / `NUMSTAT` / `STAT` 区画の出力のみ

❌ **使用禁止の情報源**: Context セクションの情報（ブランチ一覧を除く）、直近のコミット、`git status`、あなたの記憶や推測、ステップ3で取得していない情報

PR 本文に記載する全ての情報（コミット内容、ファイル名、機能名、変更内容、コミット数、ファイル数）が、ステップ3の出力から直接確認できることを確認してください。確認できない情報は含めてはいけません。

## Tips

- **複数の変更種別が混在する場合**: 最も重要な変更の種別をタイトルに使い、本文で各種別を分けて説明
- **Breaking Changes がある場合**: タイトルに ⚡️ を追加し、本文に `## ⚠️ Breaking Changes` セクションを追加
- **Issue 番号を含める場合**: 本文の最後に `Closes #123` を追加
- **リリース PR（develop → main）**: コミット数が多くなりがちなので、カテゴリ単位で要約する
- **push が前提**: 未 push のコミットは差分に含まれないので、先に `git push` しておく
- **手早く作りたい場合**: 候補1つで完結する `/ghpr-remote` を使用
