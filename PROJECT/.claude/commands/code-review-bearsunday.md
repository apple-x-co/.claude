## Context

- Changed files: !`git diff --name-only HEAD`
- Full diff: !`git diff HEAD`
- Status: !`git status --short --untracked-files=all`
- Current branch: !`git branch --show-current`

## Your task

変更されたコードを以下の観点から包括的にレビューし、日本語でフィードバックを提供します。

`Status` で `??` が付いたファイル（未追跡の新規ファイル）は `Changed files` と `Full diff` に含まれないため、Read ツールで内容を読み、ファイル全体を新規追加としてレビュー対象に含めてください。

### レビュー観点

#### 🔥 最優先: セキュリティ

コードレビュー結果の Critical に分類

- SQL インジェクション、XSS、CSRF の脆弱性
- 決済処理における機密情報の取り扱い（クレジットカード情報、トークン）
- 認証・認可の適切な実装
- セッション管理の安全性
- ファイルアップロードの検証

#### ⚡ 高優先: バグ・ロジックエラー

コードレビュー結果の Critical に分類

- Null 参照の可能性
- 型の不一致
- 境界値のチェック漏れ
- 例外処理の不備
- エッジケースの考慮不足

#### パフォーマンス

コードレビュー結果の Warning に分類

- N+1 クエリの発生
- 大容量データの処理方法（ストリーム処理 vs メモリロード）
- 不要なループやネストの深さ
- キャッシュの活用可能性
- データベースインデックスの必要性

#### コード品質

コードレビュー結果の Warning に分類

- SOLID原則への準拠
- DDD パターンの適切な使用
- 責務の分離（関心の分離）
- 命名規則の一貫性
- コードの重複（DRY原則）

#### BEAR.Sunday 固有

重大度に応じて Critical/Warning/Suggestion に分類

- DI コンテナの適切な使用
- リソース指向アーキテクチャの遵守
- インターセプターの適切な配置
- ルーティングの設計

##### グローバル値・設定

- リソース・アプリケーションクラスでスーパーグローバル（`$_GET`、`$_SERVER` 等）を参照していないか
- `define()` を使っていないか
- 設定値を保持する `Config` クラスを作っていないか
- サービスロケーター（グローバルなオブジェクトコンテナ）を使っていないか
- `date()` や `new DateTime()` で現在時刻を直接取得せず、外部から注入しているか
- static メソッド等のグローバルな呼び出しを避けているか
- 必要な値はすべて注入されているか（外部 Web API の値はクライアントクラス等の1か所に集約し、モックしやすくする）

##### クラス設計

- trait を使っていないか（`ResourceInject` 等の注入用 trait もコンストラクタプロモーションで置き換える）
- 子クラスから親クラスのメソッドを呼んでいないか（共通処理は継承ではなくクラスの注入で共有する）

##### DI

- 実行コンテキスト値（`prod`、`dev` 等）そのものを注入していないか（コンテキストに応じたインスタンスを注入する）
- ライブラリコードでセッター注入を使っていないか
- `Provider` 束縛より `toConstructor` 束縛を優先しているか
- `Module` 内で条件分岐による束縛をしていないか
- `Module` の `configure()` で環境変数を読んでいないか（コンストラクタ経由で渡す）

##### AOP・インターセプター

- インターセプターが必須の処理になっていないか（ログ、トランザクション等、無くても本質的な動作が変わらないものに限る）
- メソッド内部でしか決まらない依存をインターセプターに注入していないか（`#[Assisted]` で引数に注入する）
- 複数のインターセプターの実行順序に依存していないか
- 特定メソッドを狙ったハック目的の AOP になっていないか

##### リソース設計

- HTTP メソッドを CRUD ではなく安全性・冪等性で選んでいるか（GET は状態を変えない、PUT・DELETE は冪等）
- 適切なステータスコードを返しているか（作成は `201`、本文なしは `204`、DB 接続エラー等は `503`）
- HTML フォームでメソッドオーバーライド（`_method`、`X-HTTP-Method-Override`）を使っていないか（Page リソースは `onGet` と `onPost` のみにする）
- リンクを `#[Link]`、関連リソースを `#[Embed]` で宣言しているか
- JSON 文字列を手作りしていないか
- 未存在・削除済みを成功扱いにしていないか、not-found を汎用の RuntimeException で表していないか
- `null` と `[]` を同じ意味として扱っていないか
- embed の rel に `go*` 名を使っていないか、embed スロットを `$this->body = [...]` で上書きしていないか

##### データアクセス

- リソース内に SQL を書いていないか（Query Interface と `#[DbQuery]` を使う）
- 読み取りと書き込みのメソッドを同じインターフェースに混ぜていないか（Command と Query に分ける）
- 単純な1件取得に `SqlQueryInterface` を使っていないか
- テンプレートから DB や Query Interface を呼んでいないか

##### キャッシュ

- キャッシュ対象リソース（`#[Cacheable]`、`#[CacheableResponse]`、`#[DonutCache]`）にユーザーごとの値が混入していないか（他の訪問者にも配信されるため Critical。キャッシュしないリソースを `#[DonutCache]` ページの hole として描画する）
- `#[DonutCache]` の書き込みメソッドに、必要な `#[RefreshCache]` を付けているか（付けないと自動で purge されない）
- `#[Embed]` で表せる単一の子依存に `fromAssoc()` を使っていないか

##### 並列実行

- 並列で embed するリソースが、順序依存のない読み取り専用（GET）になっているか
- スレッドをまたぐ引数・戻り値がスカラーと配列のみになっているか（オブジェクトやクロージャは不可）
- `AsyncSwooleModule` 等を `AppModule` に直接 install していないか

##### 例外

- 入力ミス起因の例外は `RuntimeException`、バグ起因の例外は `LogicException` を継承しているか
- 例外の種類をメッセージで説明せず、種類ごとに専用の例外クラスを作っているか

##### 環境・テスト

- `.env` をリポジトリに含めていないか
- Web 専用にせず、コンソールからも動かせるようになっているか
- テストで `prod` コンテキストを使っていないか
- リソースクライアントを使ったリソーステストを中心にし、ワークフローをハイパーメディアテストで残しているか
- private メソッド単位のテストを主にしていないか

##### HTML テンプレート

- 大きなループを避けているか（ループ内の `if` はジェネレーターへの置き換えを検討する）

#### Ray.Di 固有

重大度に応じて Critical/Warning/Suggestion に分類

##### ベストプラクティス

- コンストラクタ注入と `readonly` プロパティで不変オブジェクトにしているか
- 直接の依存だけを注入しているか（別のオブジェクトを取り出すためだけにファクトリや中間オブジェクトを注入しない。必要なら Provider で取り出す）
- Injector 自体を注入していないか、Injector の使用は bootstrap での1回に留めているか
- 循環依存がないか（共有状態を新しいクラスに切り出すか、Provider を使う）
- static な状態を持っていないか
- `Module` の `configure()` が高速で副作用がないか（DB 接続等をしない）
- `Module` に条件分岐を書いていないか（環境ごとに別の Module に分ける）
- Qualifier 属性（`#[Named]`、カスタム Qualifier）を無関係な束縛に使い回していないか
- `Module` をクラスの種類ではなく機能単位でまとめているか
- `Module` が提供する公開束縛をドキュメント化しているか

##### 仕様上の制約

- インターセプター対象のクラス・メソッドが `final` でなく、メソッドが `public` で、インスタンスを `new` ではなく Ray.Di で生成しているか（満たさないとインターセプターが黙って適用されないため Critical）
- プロパティ注入を使っていないか（非対応。コンストラクタ注入かセッター注入を使う）
- 共有すべきインスタンス（PDO、キャッシュ等）に `Scope::SINGLETON` を付けているか（デフォルトは毎回新しいインスタンス）
- `#[Assisted]` の引数のデフォルト値が `null` になっているか
- 束縛の優先順位を正しく扱っているか（同じ Module 内・install 順ともに先勝ち。後から上書きするには `override()` を使う）

#### プロジェクト固有ルール

重大度に応じて Critical/Warning/Suggestion に分類

- エラーハンドリングの統一
- `fopen` 使用時のストリーム処理

### 出力形式

以下の構造で出力：

```
# コードレビュー結果

## 概要
- 変更ファイル数: X件
- 主な変更内容: [簡潔な説明]

## 🔴 Critical（必ず修正）
[セキュリティやバグなど、重大な問題]

## 🟡 Warning（推奨修正）
[パフォーマンスや保守性の問題]

## 🟢 Suggestion（改善提案）
[より良い実装方法の提案]

## ✅ Good Points
[良い実装や改善された点]
```

各指摘には：
- **ファイル名と行番号**を明記
- **問題の説明**を具体的に
- **修正案**をコード例付きで提示
- **理由**を簡潔に説明

### 重要な制約

- **全て日本語で出力**
- 指摘がない場合は「問題は見つかりませんでした」と明記
- コード例は実際に動作するものを提示
- 推測ではなく、実際の diff に基づいて判断
