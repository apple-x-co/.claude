ユーザーが特定のファイル/パスを参照する場合、説明または修正を提案する前に、それを開いて検査する必要があります。

新しい機能または抽象化を実装する前に、コードベースのスタイル、規則、および既存の抽象化を徹底的に確認してください。
根拠のある幻覚のない回答を提供してください。

## Implementation Guidelines

### 過度なエンジニアリングの禁止

**直接要求された、または明らかに必要な変更のみを実装してください。** ソリューションはシンプルで焦点を絞ったものに保つこと。

以下の行為を避けること:
* 要求されていない機能の追加
* 要求されていないコードのリファクタリング
* 「改善」と称する追加変更
* バグ修正時の周囲のコードのクリーンアップ
* シンプルな機能への不要な構成可能性の追加

### エラー処理の原則

**発生し得ないシナリオに対するエラー処理、フォールバック、検証を追加しないこと。**

* 内部コードとフレームワークの保証を信頼する
* **システム境界でのみ検証**: ユーザー入力、外部API
* 既存コードを変更できる場合は後方互換性のための中間層を作らない

### YAGNI原則 (You Aren't Gonna Need It)

* 1回限りの操作のためのヘルパー・ユーティリティ・抽象化を作成しない
* 仮説的な将来の要件のために設計しない
* **複雑さの正しい量 = 現在のタスクに必要な最小値**
* 可能な場合は既存の抽象化を再利用する
* DRY原則(Don't Repeat Yourself)に従う

## Coding Standards

### SOLID Principles

すべてのコードは以下のSOLID原則に従ってください。

* **S: Single Responsibility Principle (単一責任の原則)**
    * 1つのクラス/関数は1つの責務のみを持つこと。
    * 「変更理由」が複数ある場合は分割する。
* **O: Open/Closed Principle (オープン・クローズドの原則)**
    * 拡張に対して開き、修正に対して閉じる。新しい機能はクラスの継承やインターフェースの実装で追加し、既存のコードは修正しない。
* **L: Liskov Substitution Principle (リスコフの置換原則)**
    * サブクラスは基底クラスと置換可能であること。
* **I: Interface Segregation Principle (インターフェース分離の原則)**
    * クライアントに不要なメソッドを実装させない。巨大なインターフェースより小さなインターフェース。
* **D: Dependency Inversion Principle (依存性逆転の原則)**
    * 具象クラスではなく、抽象（インターフェース）に依存すること。
